# 30人名额变更规则与验收

版本：0.03 / CAP-T01；日期：2026-10-15；责任角色：组长与产品负责人（gpt-6-astra / high，合并承担本次派发与产品澄清）。来源：主 agent 转达用户明确授权“每间固定30人名额，1人预约时段剩29，并发防超售”。本文件是本轮容量、查询及统计的当前规则；旧版整间独占、capacity仅展示及与此冲突的验收条件已被替代。其他权限、时间、到场、违规规则继续沿用首版基线。规则制定不等于实现、独立测试或真人验收已通过。

## 1. 范围与变更故事

CAP-US01：作为学生，我希望每间自习室在同一时刻最多接受30人的预约，并看到所选时段可接受的新预约人数，以便在其他学生预约后仍能使用剩余名额。

CAP-US02：作为管理员，我希望所有房间统一为30人容量，并按人分钟查看预约率及使用率，以便统计与实际名额模型一致。

用户已确认固定30人、每单1人及防超售。以下为本次工程规则：没有座位编号、选座或一单多人；已有订单每条自动解释为占用1个名额，不重写订单历史；通过新增V3迁移统一现存房间capacity=30，包括关闭/软删除房间，后续创建及编辑只允许30。Java21 / Spring Boot、Vue2 + Element-UI、MySQL8保持既定技术栈。

## 2. 占用、余量与并发

CAP-R01：每条非CANCELLED订单在其预约区间占用1个名额，包括RESERVED、COMPLETED和NO_SHOW。只有合法取消释放原预约区间；到场、完成、爽约与违规撤销不额外释放或增加名额。原有取消时间、权限、审计与幂等规则保持适用。

CAP-R02：区间采用左闭右开 `[start,end)`。同一学生不得持有时间重叠的非取消预约，即使分别位于不同房间；同房间允许不同学生重叠预约，但任意时刻同时占用不得超过30。所有时间合法性继续由服务端按Asia/Shanghai及原开放窗口校验。

CAP-R03：查询完整时段Q时，先将与Q相交的有效订单裁剪到Q，再按时间扫描开始事件+1和结束事件−1，同一时刻结束事件先于开始事件。`occupiedSeats` 为Q内同时占用人数最大值，`remainingSeats=30-occupiedSeats`，表示能覆盖整个Q的新预约数量。不能用全部相交订单的条数代替峰值，也不能取时段开始时的占用代替全区间峰值。

例：同一房间09:00—10:00有15单，10:00—11:00有15单；查询09:00—11:00应返回occupiedSeats=15、remainingSeats=15，尽管相交订单共有30单。若两个区间各30单，则查询余量为0，但边界10:00没有60人同时占用。已有09:00—11:00的29单，新预约09:30—10:30只可再成功1单。

CAP-R04：新增订单必须在同一事务持有当前学生行锁及目标房间行锁后，重新验证封禁、房间开放状态、同学生重叠、房间时段峰值，再插入订单并提交。查询展示的余量仅为读取时的快照，不能作为之后写入成功的承诺；抢满后返回409及可理解的名额不足原因。禁止用没有锁保护的先查后插代替一致性控制。

CAP-R05：需要多个实体锁的业务统一采用用户→房间→订单顺序，涉及违规行时在所属订单后处理；不需要某类锁时可跳过，禁止逆序获取。取消、到场、违规纠错与新预约涉及同一用户或房间时必须保持此顺序；管理员关闭/删除与新增订单共享房间锁，原有“仍有未结束RESERVED则不能关闭/删除”规则继续成立。实现锁与事务的原因、边界及异常回滚须写中文注释。

## 3. API 与界面约定

既有路由、认证、订单请求/返回字段与状态码不变。变更如下：

| 接口/字段 | 当前契约 |
|---|---|
| Room.capacity | 整数30，表示可并发预约名额上限 |
| GET /api/rooms?date=…&startTime=…&endTime=… | 三项同时提供并合法时，返回每间Room的occupiedSeats、remainingSeats及available |
| Room.occupiedSeats | 完整查询区间内最大同时有效预约人数；未查询完整时段时为null |
| Room.remainingSeats | 完整查询时段为30−occupiedSeats；未提供时段时为null，不能伪装为“当前剩30” |
| Room.available | 提供时段时为房间OPEN且remainingSeats>0；不带时段时仅表示房间开放状态；关闭房间即使有余量也不可预约 |
| GET /api/rooms/{id} | 无时段参数，capacity=30，occupiedSeats/remainingSeats=null |
| POST/PUT /api/admin/rooms… | 保留capacity请求字段兼容既有结构；服务端仅接受30，非30/缺失/无效值返回400。前端表单固定只读30，不允许修改人数 |
| POST /api/orders | 每次只为当前学生创建1条1人订单；满额或本人重叠409，封禁403。成功后前端重新拉取原查询时段的房间余量 |

学生列表应明确“容量30人”“所选时段剩余X名额”；未选择完整时段应提示选择时段查看余量。没有名额或房间关闭时禁用预约入口；请求409后提示并刷新余量。取消成功后也刷新对应筛选时段。禁止仅在客户端减1作为服务端事实。

## 4. 统计口径与算例

接口字段名`reservedMinutes`、`usedMinutes`、`availableMinutes`保留，但单位均为**人分钟**；界面和说明须标明。每单1人，分子仍为各有效订单裁剪后分钟和；使用分子仍仅由COMPLETED且ARRIVED/LATE及服务器到场/完成事件支持，无证据不计。

默认每天08:00—22:00共840分钟，每间`availableMinutes=840×30=25200`人分钟。总率必须先汇总分子、分母再计算百分比；分母0返回0，最后统一保留2位小数。报表房间集合、关闭/删除处理及配置开放分钟而非历史实际营业分钟的限制延续旧基线。容量30也应用于历史日期统计；该变更是统一口径重算，不宣称旧统计历史快照得到保留。

旧合成样例按新口径：A/B各25200人分钟，共50400；A预约120人分钟、使用60人分钟，B爽约预约60人分钟；有效订单2、活动违规1不变。总预约率180/50400=0.36%，使用率60/50400=0.12%；A为0.48%/0.24%，B为0.24%/0%。另有30人各预约同一1小时时段时，预约量1800人分钟，单间日报预约率7.14%；30人占满14小时才为100%。这些为人工预期，不是执行结果。
